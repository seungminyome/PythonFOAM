## Reading change between snapshots

Each item is three times of the developed flow over the backward-facing step
(1 to 3 ms apart), in one random window. The model returns three words: the
peak-speed trend (increasing, decreasing, roughly constant), the lowest-pressure
trend (more negative, less negative, roughly constant) and whether the fastest
spot moves. The answer key uses 2 % relative change and 5 % of the plotted
range. The 45 items were chosen to cover the speed-pressure combinations:
15 of each speed word; 20, 18 and 7 of the pressure words. Each item was asked
in five forms:

| Form | What the model gets |
|---|---|
| v1 | the solver's two-panel pictures, one per time, and the October 20 prompt |
| v2own | one picture per field and time, each on its own colour scale; the prompt says to compare the colour-bar numbers (October 22) |
| v2own + thresholds | the same, with the key's 2 % and 5 % rules in the prompt |
| v2own + numbers | the same, plus each time's largest \|U\| and lowest p in the note |
| numbers only | the numbers and the rules, no pictures |

NVIDIA L40S):

- With the solver's v1 pictures no model did clearly better than one fixed
  answer (14 to 18 of 45 for speed against 15, 15 to 20 for pressure against
  20). One picture per field on its own colour scale, with the extremes
  printed on the colour bar, about doubles the count (31 to 32 of 45 for
  speed).
- On clear changes, 12B with v2own pictures read the speed trend right in 29
  of 30. Its errors are mostly on the 15 items whose speed changed by less
  than 2 %, which it nearly never called roughly constant (3 times in 45).
  Stating the 2 % rule in the prompt raised 12B's count on those 15 items
  from 3 to 7, and did not help the pressure trend.
- The other models with v2own pictures read 17 to 25 of the 30 clear speed
  changes (26B-A4B 25, 31B 20, Qwen3.5 17): most of their errors are on clear

  against a 2 % rule is not reliable in these models.
- The region word is not informative here: 39 of 45 items "move", and one
  fixed answer gets 39.

## 4-bit Qwen with the recommended image tokens

On October 22 the Qwen models ran in Q8_0 (Gemma in 4-bit) and below the
image-token minimum llama.cpp recommends for them. Here the three larger Qwen
models ran as Q4_K_M files with `--image-min-tokens 1024` and
`--image-max-tokens 1024` (context 8192), on the two random-window sets of
October 22 (jobs 24903976 and 24903977, NVIDIA L40S). v2 pictures; within
10 % of the plotted range:

| Model | `seed1` (48), fastest / lowest p | `developed` (140), fastest / lowest p | Median time per request (developed) |
|---|---:|---:|---:|
| Qwen3.5-35B-A3B Q4_K_M | 48 / 46 | **133 / 137** | 2.0 s |
| Qwen3.5-27B Q4_K_M | 48 / 48 | 128 / 136 | 6.1 s |
| Qwen3-VL-32B Q4_K_M | 38 / 46 | 112 / 134 | 7.6 s |
| *October 22:* Gemma 4 12B / 26B-A4B / 31B | 45 to 47 / 47 to 48 | 106 to 113 / 130 to 139 | 2.4 to 7.3 s |
| *October 22:* Qwen3.5-35B-A3B Q8_0, 256 image tokens | 47 / 46 | 121 / 134 | 2.1 s |
| One fixed answer | 7 / 7 | 16 / 17 | |

- With these settings Qwen3.5-35B-A3B and Qwen3.5-27B place the fastest flow
  in the developed flow more often than any Gemma model (133 and 128 of 140
  against 106 to 113); on the lowest pressure all are close (Qwen3.5 136 to
  137, Gemma 130 to 139).
- The settings are not equal: the Qwen files are Q4_K_M with 1024 image
  tokens and context 8192, the Gemma files QAT Q4_0 with 256 image tokens
  (which the Gemma requests do not reach) and context 4096, and the GPU
  differs (L40S here, RTX A6000 on October 22). Two things changed for Qwen
  at once (4-bit files and the image-token setting), so the gain is not
  attributed to one of them. With `--image-max-tokens 1024` alone the two
  Qwen3.5 Q8_0 files already reached 47 to 48 of 48 on `seed1` on October 22.
- A Qwen request is about 2,590 prompt tokens with these settings, a Gemma
  request about 1,050.

## A request every 250 steps

`LLM_ANALYSIS_EVERY=250` with `LLM_MODE=describe`, v2 pictures and one request
in flight at most: 24,000 steps of 5×10⁻⁶ s from t = 0.1 s of the developed
flow, Gemma 4 12B QAT on an NVIDIA A30 (job 24903264), and the same run
without requests on the same node. The plotted window is fixed (x 0 to 0.12 m,
y 0 to 0.04 m).

| | Without requests | With 96 requests |
|---|---:|---:|
| Requests answered | | 96 of 96 |
| Written files identical to the other run | 2,016 of 2,016 | |
| Wall time per step | 0.05794 s | 0.05833 s (+0.7 %) |
| Callback time at a request step | | at most 0.017 s (the last step: 6.8 s, see below) |
| Reply arrived after | | 85 to 144 steps (model time 4.2 to 5.3 s); the last request is waited for at the last step |
| Bytes back over the pipe per request | | 4,009 to 4,461 |
| Request body | | 212 to 230 kB |
| Solver process memory (PSS) at the low point of each 250-step cycle, first to last quarter of the run | 131 → 216 MiB | 173 → 243 MiB |
| llama-server memory (RSS) | | 12.5 GiB |
| Fastest flow within 10 % | | 65 of 96 (one fixed answer: 53) |
| Lowest pressure within 10 % | | 89 of 96 (one fixed answer: 65) |

<img src="evidence/2026-10-27-solver/periodic/tracking.png" width="760" alt="True x and answered x of the lowest pressure and the fastest flow over the run">

*x position, in percent of the plotted range, of the lowest pressure (top) and the fastest flow (bottom) at each request, true (line) and 12B's answer (dots).*

- The solver ran at its own pace: 0.7 % slower, the callback never taking
  more than 0.017 s at a request step (the last step waits for the pending
  reply by design, 6.8 s), with every written file equal to the run without
  requests. The run without requests drew the same 96 pictures, so 0.7 % is
  the cost of the requests on top of drawing. It is one pair of runs, on a
  node where three other jobs of this study ran at the same time.
- The lowest pressure jumps between vortex cores from one request to the next
  (x from 28 to 80 %); the answers follow it with correlation 0.78 in x
  ([tracking.py](evidence/2026-10-27-solver/periodic/tracking.py)). The
  fastest flow is followed less (0.35): 93 of the 96 answers lie between 35
  and 65 % while the true spot reaches 19 and 81 %.
- Of the 31 fastest-flow answers more than 10 % off, 27 named a spot with at
  least 90 % of the largest speed in the plotted range (all at least 86 %);
  of the 7 lowest-pressure misses, 5 named a spot at least 90 % as low. In
  this flow the wrong answers pick a near-equal second candidate, unlike
  12B's pressure misses on the cylinder (15 to 61 % of the minimum)
  ([misses.py](evidence/2026-10-27-solver/periodic/misses.py)).
- Memory. The case's POD module keeps 250 snapshots and clears them at each
  SVD, so the solver process swings by up to 430 MiB within every 250-step
  cycle. At the low point of each cycle it grows by about the same amount
  without and with requests (+85 and +70 MiB over 24,000 steps), so the
  requests do not add to it. About 32 MiB of it is the callback's per-step
  history, which it keeps for `telemetry.jsonl` (1.35 KiB per step); the rest
  was not traced ([memory.py](evidence/2026-10-27-solver/periodic/memory.py)).

## MPI and the POD files

- **MPI.** In a parallel run the observer now gathers the mesh and the fields
  to the master rank, and only the master calls `mesh_func` and
  `analysis_func`; the POD snapshot and SVD stay per rank. On 2 ranks (scotch
  decomposition, 600 steps, frame at step 100, no model; job 24903786) the
  frame has the same 20,540 cells as the serial run's, cell centres equal to
  4×10⁻¹⁷ m, U within 7.5×10⁻⁴ m/s (of 37 m/s) and p within 0.021 m²/s² (of
  335), the differences of a parallel solve. The bridge validation passes with
  the same build.
- **POD files.** On October 22 the sweep's POD mode files differed from the
  baseline's by up to 10⁻¹¹ of the largest value while U, p and phi were
  identical. Six runs of 600 steps (job 24903065): with 8 BLAS threads all 30
  mode files differ from a one-thread run, alone or two at once, by at most
  1.0×10⁻¹³ (10⁻¹² of the largest value); with one thread all 42 written
  files are identical, also two at once. The cause is the thread count of the
  SVD, not the requests or a second solver.

## An unstable flow

A picture of a run going wrong would be the natural test of whether a model
notices it. Nine attempts on the step flow with `pimpleFoam` did not produce
one ([summary](evidence/2026-10-27-solver/unstable/unstable-summary.json)):
with upwind convection every run finished, up to a Courant number of 28; with
central differencing the runs stopped with a floating point exception at the
first step (Courant number 4.5 and 11) or finished without visible
oscillation (1.54 and below, judged by eye). This test is not done.

## What this shows and what it does not

- With each picture on its own scale and its extremes printed, every model
  reads about twice as many trends right as with the solver's old pictures.
  12B then reads clear speed changes (29 of 30) and misses most changes under
  2 %; the other models also miss clear changes. With the numbers only, 31B
  read every clear change.
- With 4-bit files and the image-token setting llama.cpp recommends, Qwen3.5
  models place the fastest flow of the developed flow more often than Gemma
  (with Gemma's own settings), and are close on the lowest pressure.
- The method transfers to another 2D geometry for the fastest flow; for a
  small pressure spot beside a large dark region only the largest model is
  reliable.
- Requests every 250 steps cost 0.7 % of run time on top of drawing the
  pictures (one pair of runs) and do not change the computation; the answers
  follow the lowest pressure as it moves between vortex cores, and when they
  miss in this flow they name a near-equal second candidate.
- Same request, same node: same answer. Another GPU: other text and some
  other positions, the same counts within 10 % in the sweep, and one trend
  word changed (wrong on the A6000, right on the A30).
- The observer runs in parallel (2 ranks, one 2D case).

Not shown:

- 3D cases, more than 2 ranks, and a parallel run with a model request.
- More than one request in flight.
- A run going unstable, and whether a model would notice it.
- All of the memory growth over long runs: about 32 of the 70 to 85 MiB is
  traced.
- The descriptions themselves; only positions and trend words are scored.
- Any use of the answers. Nothing from the model goes back into the solver.
