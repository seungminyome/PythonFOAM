## Two requests in flight

A v2 describe request every 50 steps with at most two pending
(`LLM_ASYNC_MAX_PENDING=2`) and a server with two slots (`LLM_PARALLEL=2`),
6,000 steps from the developed flow, and the same run without requests
(job 24929296, Gemma 4 12B, NVIDIA L40S). Against the October 27 run with
one request every 250 steps ([inflight.py](evidence/2026-10-28-inflight/inflight.py)):

| | Two in flight, every 50 steps | One in flight, every 250 steps |
|---|---:|---:|
| Requests planned / answered | 120 / 118 | 96 / 96 |
| Skipped because two were pending | 2 | 0 |
| Sent while another request was pending | 112 | 0 |
| Written files identical to the run without requests | 2,520 of 2,520 | 2,016 of 2,016 |
| Wall time per step, without / with requests | 0.06165 / 0.06363 s (+3.2 %) | 0.05794 / 0.05833 s (+0.7 %) |
| Extra wall time per answered request | 0.101 s | 0.097 s |
| Callback time at a request step, largest (last step excepted) | 0.046 s | 0.017 s |
| Model time, smallest / median / largest | 2.54 / 3.80 / 4.65 s | 4.15 / 4.73 / 5.25 s |
| Fastest flow within 10 % (one fixed answer) | 81 of 117 (62) | 65 of 96 (53) |
| Lowest pressure within 10 % (one fixed answer) | 106 of 117 (78) | 89 of 96 (65) |

- Two requests ran side by side, and a step that found two pending was
  skipped and recorded, as designed.
- Each request costs about 0.1 s of solver wall time in both runs, on top of
  drawing the pictures (the runs without requests drew them too), so five
  times as many requests cost about five times as much. One pair of runs
  each, on different nodes.
- One reply was not recorded. The request of step 4100 was answered (step
  4167), but the forked writer that writes its record is stopped after 0.2 s
  so that the solver never waits longer, and that step took 0.207 s: the
  folder has no `llm_result.json`, while the index said `ok`. The solver was
  not affected. The index now records `record_written` for every request
  (`56646b9`), and `run_periodic.py --summary-only` lists such requests and
  leaves them out of the scores (`c85c79c`).

## The callback's telemetry without a history

The callback kept every step's state until the end of the run to write
`telemetry.jsonl` (32 MiB over 24,000 steps). It now encodes each step's line
when the step arrives and appends the lines in batches (every 500 lines or
60 s, and at the last step) from a forked writer with a 0.2 s deadline,
keeping only the first state and the last three
([callback evidence](evidence/2026-10-28-callback/README.md), job 24929555):

| | Before | Now |
|---|---:|---:|
| Python heap over the 24,000 recorded states of October 27 (replay, `memory.py`) | 31.7 MiB | at most 0.52 MiB (0.07 MiB after an append) |
| The last step, which writes the file (replay) | 0.699 s | 0.023 s |
| Callback time per ordinary step in PODFoam, median | 0.08 to 0.11 ms | 0.16 to 0.22 ms |
| Steps with an append (steps 500 and 1,000) | – | 13.7 to 22.0 ms |
| `telemetry.jsonl` | | byte-identical in the three solver pairs (1,250 steps; serial describe, serial sequence, 2 ranks) and in the 24,000-state replay |

- Every written field, frame and request body of the runs with the new
  callback equals the runs with the old one.
- The file is complete or absent: during the run only
  `telemetry.jsonl.tmp` exists, and it is renamed at the last step. A write
  that fails is reported once in `llm_errors.jsonl`; the solver never stops.
- Each ordinary step now costs about 0.1 ms more, because its line is encoded
  in the solver process.

## Computed trend words

For a v2 sequence the callback now computes the three trend words from the
frames' arrays inside the plotted range, with the answer key's rules (2 %
relative change, 5 % of the range for the spot), and records them in
`llm_result.json` (`computed_trends`, and `computed_trends_agreement` when the
model answered). The request is unchanged. In the solver run with frames at
steps 100, 150 and 200 they were `increasing` (+2.44 %), `more_negative`
(−10.9 %) and `moves` (6.92 % of the range), the same as the picture tests'
answer key. `LLM_SEQUENCE_PROMPT=t` or `tn` sends the October 27 forms with
the thresholds, or the thresholds and each time's extrema; the default sends
the October 22 request byte for byte. In these runs no model answered, so
the agreement field was checked only against a test server.

## 3D cases: a plane slice

v2 pictures needed one polygon per cell from the empty patch of a 2D case.
For a 3D mesh, PODFoam now cuts it with OpenFOAM's `cuttingPlane` at
z = `LLM_SLICE_Z` (default the middle of the z range, moved off a plane of
mesh points), and the observer draws the cut cells, each as its own polygon
([3D evidence](evidence/2026-10-28-3d/README.md)). The test case is the step
case extruded to 8 cells in z with walls front and back (164,320 cells),
started from the 2D state at t = 0.1 s, 150 steps (job 24929629):

- The slice holds 20,540 cells, one per 2D cell, in the fifth layer.
- On 2 ranks it has the same cells as the serial run: centres equal to
  4.2×10⁻¹⁷ m, polygon vertices identical, U within 2.5×10⁻³ m/s (of 37.2) and
  p within 0.036 m²/s² (of 282).
- The frame equals the written fields of its step to their 12 digits; all
  63 written files equal a run without the observer; the request body equals
  the tested builder applied to the frame.
- A bad `LLM_SLICE_Z`, or a plane that cuts no cells, gives a solver warning
  and a refused request; the runs went on to the end.
- 2D cases are unchanged: the 2D frame and request body equal those of the
  October 27 MPI test file for file, and the bridge validation passes.

## Can a model see a run going unstable?

Runs of the step case with central differencing and a larger time step crash
after some steps: `central-dt3e-5` in step 27, `central-dt4e-5` in step 10,
and `central-dt2e-5` in step 467 when run on. Four models were shown three v2
frames (|U| and p, each on its own colour scale, in the solver's window) and
asked whether the run shows signs of numerical instability: 27 triples whose
last frame is 1 to 10 steps before a crash, and 27 from runs that ended
(upwind runs, the developed flow, a central run with a small time step)
([instability evidence](evidence/2026-10-28-instability/README.md), jobs
24929533 and 24929534, NVIDIA L40S):

| Answers from | Right of 54 | Crash coming, said `unstable` (of 27) | Run ended, said `stable` (of 27) |
|---|---:|---:|---:|
| Gemma 4 12B | 32 | 5 | 27 |
| Gemma 4 26B-A4B | 30 | 3 | 27 |
| Gemma 4 31B | 33 | 6 | 27 |
| Qwen3.5-35B-A3B Q8_0 | 32 | 5 | 27 |
| One fixed answer | 27 | | |
| Rule: peak \|U\| in the window grows more than 20 % | 33 | 6 | 27 |
| Rule: largest cell-to-cell \|U\| jump grows more than 50 % | 38 | 11 | 27 |

- Every model said `unstable` for the 3 triples whose last frame is the step
  before a crash, where the field has already blown up (largest |U| 84.6 m/s
  to 1.5×10⁴⁰ m/s). Besides those, 0 to 3 more, the earliest 5 steps before
  its crash. No model called a run that ended `unstable`.
- Every triple a model called `unstable` had its peak |U| grow by 30.8 % or
  more; a rule on that number alone does as well as the best model, and a
  rule on the cell-to-cell jump does better. On this set the pictures added
  nothing beyond the colour-bar numbers.
- The set has a flaw: each request states the frames' times, and the frames
  of the crashed runs are closer together than those of the runs that ended,
  so the time between frames alone separates the classes (54 of 54). The
  negative result stands, because the models said `stable` for most crashed
  runs.

## What this shows and what it does not

- The asynchronous path keeps two requests going without slowing the solver
  beyond about 0.1 s per request, and every written file stays the same.
- The callback's memory no longer grows with the run; its telemetry file is
  byte-identical to before.
- Trend words can be computed exactly in the callback and recorded next to
  the model's.
- The observer draws v2 pictures of a 3D case through a plane slice, also on
  2 ranks.
- The models tested do not warn of a coming crash from the pictures; they
  see a run that has already blown up.

Not shown:

- A model reading a slice picture; other 3D meshes or plane directions.
- Computed trend words next to a live model's answer.
- A crash warning earlier than a few steps, from pictures or numbers; a set
  without the stated-time flaw.
- More than two requests in flight; the record writer under a slow disk
  (one of 118 records was lost).
- Any use of the answers. Nothing from the model goes back into the solver.
